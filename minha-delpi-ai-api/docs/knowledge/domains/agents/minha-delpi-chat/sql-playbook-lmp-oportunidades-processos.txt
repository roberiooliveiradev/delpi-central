10. REGRA DE NÚMERO DA OPORTUNIDADE
======================================================================

O campo da oportunidade é textual e tem 6 posições:

- AD1_NROPOR
- ADJ_NROPOR
- AIJ_NROPOR

Sempre tratar número da oportunidade com zeros à esquerda.

Exemplo:
Usuário informa:
- 102
- 00102

Pesquisar também:
- 000102

Regra prática:
Se a busca exata não retornar dados, executar busca auxiliar:

AD1_NROPOR LIKE '%<numero_sem_zeros>%'

Depois informar ao usuário o número correto encontrado.

Nunca afirmar que uma oportunidade não existe antes de testar variações com zeros à esquerda.

13. REGRAS PARA DIAGNÓSTICO DA LISTAGEM LMP
======================================================================

A listagem LMP depende de uma regra de entrada por processo/estágio.

As configurações conhecidas são:

### lmp_anchor_process_stages
Define quais processos/estágios fazem uma oportunidade entrar na listagem LMP.

Exemplo validado:
000002 -> 000003, 000012
000003 -> 000003, 000012

Interpretação:
- processo 000002, estágio 000003 = ENGENHARIA
- processo 000002, estágio 000012 = LANCAMENTO / HOMOLOGACAO
- processo 000003, estágio 000003 = conforme cadastro AC2010
- processo 000003, estágio 000012 = conforme cadastro AC2010

### engineering_support_process_stages
Define quais processos/estágios são considerados apoio/suporte de engenharia.

Exemplo:
000002 -> 000003, 000008, 000012
000003 -> 000003, 000012

Para diagnosticar por que uma oportunidade não aparece:
1. Confirmar se existe na AD1010.
2. Confirmar número correto com 6 dígitos.
3. Confirmar filial.
4. Confirmar revisão.
5. Verificar se possui histórico na AIJ010.
6. Verificar se em algum momento passou por processo/estágio configurado em lmp_anchor_process_stages.
7. Se passou por Engenharia, mas não está no anchor, sugerir ajuste de settings.
8. Se não passou por nenhum estágio configurado, informar que não atende à regra da listagem.

======================================================================
14. REGRAS DE NEGÓCIO OFICIAIS DA API LMP
======================================================================

Este agente deve interpretar LMP conforme as regras reais da API DELPI.

A API LMP não trata toda oportunidade como LMP.
Uma oportunidade só entra na listagem LMP quando possui evento histórico na AIJ010 que corresponda aos estágios configurados em lmp_anchor_process_stages.

----------------------------------------------------------------------
14.1. FILIAIS PADRÃO
----------------------------------------------------------------------

As filiais padrão da LMP são:

- 01
- 02

Se o usuário não informar filial, consultar as filiais configuradas.

Configuração:

branches = ["01", "02"]

----------------------------------------------------------------------
14.2. EVENTOS ÂNCORA DA LMP
----------------------------------------------------------------------

A entrada de uma OV na listagem LMP depende dos eventos âncora:

Processo 000002 - OPORTUNIDADE:
- 000003 = ENGENHARIA
- 000012 = LANCAMENTO / HOMOLOGACAO

Processo 000003:
- 000003
- 000012

Configuração oficial:

lmp_anchor_process_stages = {
"000002": ["000003", "000012"],
"000003": ["000003", "000012"]
}

Regra:
- Se a OV não tiver nenhum evento AIJ010 nesses processo/estágio, ela não é candidata LMP.
- Se tiver evento âncora, a LMP_START_DATE é a data AIJ_DTINIC do evento âncora mais recente.
- A LMP_END_DATE é AIJ_DTENCE; se AIJ_DTENCE estiver vazio, a API tenta resolver pela próxima movimentação histórica da OV.
- A escolha do evento âncora mais recente usa:
1. AIJ_REVISA DESC
2. AIJ_DTINIC DESC
3. AIJ_HRINIC DESC
4. R_E_C_N_O_ DESC

----------------------------------------------------------------------
14.3. EVENTOS DE FOLLOW-UP LMP
----------------------------------------------------------------------

Os estágios de acompanhamento posterior são:

lmp_followup_process_stages = {
"000002": ["000013"],
"000003": ["000013"]
}

Use estes estágios para análises de continuidade/acompanhamento, mas não como regra principal de entrada da LMP.

----------------------------------------------------------------------
14.4. EVENTOS DE APOIO / SUPORTE DE ENGENHARIA
----------------------------------------------------------------------

A API considera os seguintes estágios como eventos de Engenharia:

engineering_support_process_stages = {
"000002": ["000003", "000008", "000012"],
"000003": ["000003", "000012"]
}

Interpretação:
- 000002 / 000003 = ENGENHARIA
- 000002 / 000008 = AMOSTRA ENGENHARIA
- 000002 / 000012 = LANCAMENTO / HOMOLOGACAO
- 000003 / 000003 = conforme cadastro AC2010
- 000003 / 000012 = conforme cadastro AC2010

Regra:
- Para saber se uma OV passou pela Engenharia, consultar AIJ010 usando estes estágios.
- Para saber se uma OV entra na LMP, usar lmp_anchor_process_stages.
- Não confundir suporte de Engenharia com âncora LMP.

----------------------------------------------------------------------
14.5. STATUS DE ENGENHARIA
----------------------------------------------------------------------

A API usa os seguintes status de engenharia:

- ABERTA
- FINALIZADA
- PARCIAL
- RETORNADA

Configuração:

engineering_status_labels = {
"in_progress": "ABERTA",
"finished": "FINALIZADA",
"partial": "PARCIAL",
"returned": "RETORNADA"
}

Regra para interpretação:

1. RETORNADA
Quando há evento de Engenharia aberto/vazio que depois segue para evento não Engenharia com revisão maior ou estágio menor.

2. ABERTA
Quando há evento de Engenharia sem encerramento e não há próximo evento global.

3. FINALIZADA
Quando todos os eventos da última revisão de Engenharia possuem encerramento ou próximo evento global que permita medir saída.

4. PARCIAL
Quando não se enquadra plenamente como aberta, finalizada ou retornada.

Nunca inventar status.
Sempre calcular ou reproduzir conforme os eventos AIJ010.

----------------------------------------------------------------------
14.6. MEDIÇÃO DA ÚLTIMA REVISÃO DE ENGENHARIA
----------------------------------------------------------------------

A API mede a Engenharia com base na última revisão relevante.

A escolha da revisão de medição prioriza:
1. revisões que contenham evento âncora LMP;
2. maior revisão disponível.

Regra:
- A análise de tempo de Engenharia não deve somar aleatoriamente todas as revisões.
- A API usa a última revisão de medição definida por ranking.
- Para diagnóstico detalhado, mostrar todas as revisões, mas para status e SLA, respeitar a última revisão de medição.

----------------------------------------------------------------------
14.7. TEMPO TOTAL DE ENGENHARIA
----------------------------------------------------------------------

A API calcula TEMPO_TOTAL_MINUTOS_ENG somando, para cada evento de Engenharia:

- início = AIJ_DTINIC + AIJ_HRINIC
- fim =
1. AIJ_DTENCE + AIJ_HRENCE, se existir;
2. próxima data/hora de evento global, se existir;
3. GETDATE(), se ainda estiver em aberto.

Regra:
- Tempo de Engenharia é medido em minutos.
- Se o evento está aberto, o tempo conta até agora.
- Se existe próximo evento global, ele pode ser usado como ponto de saída da Engenharia.
- Se AIJ_DTINIC ou AIJ_HRINIC estiverem vazios, considerar 0 minuto para aquele evento.

----------------------------------------------------------------------
14.8. AVANÇOU OU RETORNOU DA ENGENHARIA
----------------------------------------------------------------------

A API calcula:

QTD_AVANCOU_ENG:
- quando o evento de Engenharia foi encerrado ou possui próximo evento;
- o próximo evento não é Engenharia;
- está na mesma revisão;
- o próximo estágio é maior que o estágio atual.

QTD_RETORNOU_ENG:
- quando o evento de Engenharia foi encerrado ou possui próximo evento;
- o próximo evento não é Engenharia;
- e:
- a próxima revisão é maior que a revisão atual; ou
- o próximo estágio é menor que o estágio atual.

Interpretação:
- Avançou = saiu da Engenharia seguindo o fluxo.
- Retornou = voltou/reabriu/revisou fluxo de Engenharia.

----------------------------------------------------------------------
14.9. CONTAGEM DE PI
----------------------------------------------------------------------

A API calcula QTD_PI a partir dos produtos da oportunidade.

Fluxo oficial:

1. Buscar produtos da LMP em ADJ010.
2. Cruzar ADJ_PROD com SB1010.B1_COD.
3. Usar B1_REFEREN para encontrar o produto raiz do tipo PA.
4. Explodir estrutura SG1010 a partir do PA.
5. Contar componentes distintos cujo tipo em SB1010 seja PI.
6. Somar a quantidade de PI por OV/revisão.

Configurações:

root_product_types = ["PA"]
pi_product_types = ["PI"]
max_bom_level = 10

Regras:
- A contagem de PI não é simplesmente a quantidade de itens ADJ010.
- A contagem vem da estrutura/BOM via SG1010.
- A estrutura válida exige G1_FIM > data atual no formato YYYYMMDD.
- A recursão máxima é 10 níveis.
- Somente componentes SB1010.B1_TIPO = 'PI' entram na contagem.
- Produto raiz deve ser SB1010.B1_TIPO = 'PA'.
- Se B1_REFEREN estiver vazio, o produto não contribui para a contagem de PI.

----------------------------------------------------------------------
14.10. NÍVEL DA LMP
----------------------------------------------------------------------

O nível da LMP é calculado pela quantidade de PI:

- QTD_PI <= 10 -> Nível 1
- QTD_PI <= 20 -> Nível 2
- QTD_PI > 20 -> Nível 3

Regra:
- Se QTD_PI estiver nulo, considerar 0.
- QTD_PI nulo ou 0 resulta em Nível 1.

----------------------------------------------------------------------
14.11. SLA POR NÍVEL
----------------------------------------------------------------------

O SLA oficial é:

- Nível 1 = 4 dias úteis
- Nível 2 = 8 dias úteis
- Nível 3 = 20 dias úteis

Configuração:

SLA_BY_LEVEL = {
"Nível 1": 4,
"Nível 2": 8,
"Nível 3": 20
}

A API também calcula SLA em minutos:

- 1 dia = 24 horas
- 1 dia = 1440 minutos

Portanto:
- Nível 1 = 4 * 1440 = 5760 minutos
- Nível 2 = 8 * 1440 = 11520 minutos
- Nível 3 = 20 * 1440 = 28800 minutos

----------------------------------------------------------------------
14.12. TOLERÂNCIA DE SLA
----------------------------------------------------------------------

A API aplica tolerância de 1 dia útil ao SLA.

Configuração:

SLA_TOLERANCE_DAYS = 1

Limite final em dias:
- Nível 1 = 4 + 1 = 5 dias úteis
- Nível 2 = 8 + 1 = 9 dias úteis
- Nível 3 = 20 + 1 = 21 dias úteis

Limite final em minutos:
- SLA em minutos + 1440 minutos

Regra:
- A data limite oficial do dashboard usa dias úteis.
- A comparação por minutos usa SLA + tolerância.

----------------------------------------------------------------------
14.13. DIAS ÚTEIS
----------------------------------------------------------------------

A API considera dias úteis excluindo sábado e domingo.

Regra:
- Sábado e domingo não contam como dia útil.
- Feriados não são tratados na regra atual.
- add_business_days soma dias ignorando fins de semana.
- business_days_between conta dias úteis entre início e fim, incluindo as extremidades.

----------------------------------------------------------------------
14.14. DATA LIMITE DA LMP
----------------------------------------------------------------------

A data limite é calculada a partir de LMP_START_DATE:

1. Calcular data limite base:
start_date + SLA em dias úteis

2. Calcular data limite com tolerância:
data limite base + 1 dia útil

A API retorna no dashboard:
- data_limite = data limite base sem tolerância

Mas para classificação de atraso usa:
- data limite com tolerância

Regra:
- Ao explicar o status, diferenciar data_limite exibida e tolerância usada no cálculo.

----------------------------------------------------------------------
14.15. LEAD TIME ÚTIL
----------------------------------------------------------------------

Lead time útil é calculado quando existem:

- start_date
- end_date

Fórmula:
- contar dias úteis entre start_date e end_date, incluindo início e fim.

Se não houver end_date:
- lead_time_util = null

----------------------------------------------------------------------
14.16. STATUS DO DASHBOARD
----------------------------------------------------------------------

A API usa os seguintes status no dashboard:

- Pontual
- Atrasado
- Andamento
- Retornada

Regras:

1. Se engineering_status = RETORNADA:
status = Retornada

2. Se engineering_status = FINALIZADA:
Verificar:
- end_date <= data_limite_com_tolerancia
OU
- engineering_total_minutes <= sla_limit_minutes

Se uma das duas condições for verdadeira:
status = Pontual

Caso contrário:
status = Atrasado

3. Se engineering_status não for FINALIZADA nem RETORNADA:
Verificar:
- hoje > data_limite_com_tolerancia
E
- engineering_total_minutes > sla_limit_minutes

Se as duas condições forem verdadeiras:
status = Atrasado

Caso contrário:
status = Andamento

Regra importante:
- Para LMP finalizada, basta estar dentro do prazo por data OU por minutos para ser Pontual.
- Para LMP aberta/em andamento, só é Atrasado se estourar data E minutos.
- Retornada sempre prevalece sobre todos os outros status.

----------------------------------------------------------------------
14.17. RESUMO DO DASHBOARD
----------------------------------------------------------------------

O resumo do dashboard calcula:

- total_lmps = quantidade total de LMPs retornadas
- percent_dentro_prazo = percentual de LMPs cujo status não é Atrasado
- avg_lead_time = média do lead_time_util apenas das LMPs com lead_time_util preenchido

Regra:
- Retornada conta como dentro do prazo para o percentual, pois só Atrasado é excluído.
- Andamento também conta como dentro do prazo.
- Se total_lmps = 0, percent_dentro_prazo = 0.0
- Se não houver lead_time_util, avg_lead_time = 0.0

----------------------------------------------------------------------
14.18. FILTRO DE STATUS DO DASHBOARD
----------------------------------------------------------------------

A listagem do dashboard pode filtrar por status:

- Todos
- Pontual
- Atrasado
- Andamento
- Retornada

Regra:
- Se status_filter = Todos, não filtrar.
- Caso contrário, retornar apenas itens cujo status calculado seja igual ao filtro.

----------------------------------------------------------------------
14.19. PAGINAÇÃO
----------------------------------------------------------------------

A listagem LMP suporta paginação.

Regra:
- Se page_size não for informado, retornar todos os itens encontrados:
- page = 1
- page_size = total

- Se page_size for informado:
- page padrão = 1
- offset = (page - 1) * page_size
- usar OFFSET / FETCH

----------------------------------------------------------------------
14.20. GET LMP INDIVIDUAL
----------------------------------------------------------------------

Para buscar uma LMP individual, a API:

1. Busca cabeçalho em AD1010.
2. Exige evento LMP em LMPEventos.
3. Enriquece com resumo de Engenharia.
4. Enriquece com cliente SA1010.
5. Enriquece com vendedor SA3010.
6. Busca produtos vinculados.
7. Calcula QTD_PI total.
8. Calcula nível, SLA, data limite, lead time útil e status.

Regra:
- Se não houver header_row, retornar erro:
LMP não encontrada: <sale_number>

Interpretação:
- Uma OV pode existir na AD1010, mas não ser uma LMP válida para a API se não tiver evento âncora LMP.
- Por isso, diagnóstico deve separar:
- existe como oportunidade;
- existe como LMP;
- passou por Engenharia;
- passou por evento âncora;
- aparece na listagem.

----------------------------------------------------------------------
14.21. DIFERENÇA ENTRE OV, LMP E DASHBOARD
----------------------------------------------------------------------

OV:
- Registro de oportunidade em AD1010.

LMP:
- OV que possui evento âncora em AIJ010 conforme lmp_anchor_process_stages.

Dashboard LMP:
- LMP enriquecida com:
- resumo de Engenharia;
- QTD_PI;
- nível;
- SLA;
- data limite;
- lead time útil;
- status calculado.

Regra:
- Nunca afirmar que uma OV é LMP apenas por existir na AD1010.
- Nunca afirmar que uma OV não existe apenas porque não aparece na listagem LMP.
- Primeiro verificar AD1010, depois AIJ010, depois regra de âncora.

----------------------------------------------------------------------
14.22. DIAGNÓSTICO INTELIGENTE DE “NÃO APARECE NA LMP”
----------------------------------------------------------------------

Quando o usuário perguntar por que uma OV não aparece na LMP, seguir esta ordem:

1. Normalizar número da OV para 6 dígitos.
2. Consultar AD1010:
- existe?
- filial?
- revisão?
- descrição?
- processo atual?
- estágio atual?

3. Consultar AC1010 e AC2010:
- descrição do processo atual;
- descrição do estágio atual.

4. Consultar AIJ010:
- todos os eventos da OV;
- revisões;
- processos;
- estágios;
- datas;
- status;
- encerramentos.

5. Marcar em cada evento:
- passou em lmp_anchor_process_stages?
- passou em engineering_support_process_stages?

6. Concluir:
- não existe na AD1010;
- existe, mas número informado estava sem zeros;
- existe, mas não possui histórico AIJ010;
- existe, passou por Engenharia, mas não por âncora LMP;
- existe e passou por âncora LMP, então deveria aparecer;
- existe como OV, mas não como LMP válida;
- está fora por filtro de data;
- está fora por filtro de filial;
- está fora por status calculado no dashboard.

----------------------------------------------------------------------
14.23. STATUS EXPLICATIVO PARA RESPOSTAS
----------------------------------------------------------------------

Quando responder ao usuário, usar linguagem clara:

- “Existe como oportunidade, mas não entra como LMP porque não possui evento âncora.”
- “A OV passou pela Engenharia, mas não está no estágio configurado como entrada LMP.”
- “A OV já é candidata LMP, pois passou pelo processo/estágio configurado.”
- “O status do dashboard é Atrasado porque excedeu data limite com tolerância e minutos de SLA.”
- “O status é Pontual porque, apesar da data, ficou dentro do limite de minutos.”
- “O status é Retornada porque a regra de Engenharia marcou retorno.”
- “O status é Andamento porque ainda não finalizou e não ultrapassou simultaneamente data e minutos.”

----------------------------------------------------------------------
14.24. CAMPOS CALCULADOS QUE O ESPECIALISTA DEVE SABER EXPLICAR
----------------------------------------------------------------------

O especialista deve conseguir explicar:

- start_date:
data de início LMP, baseada no evento âncora.

- end_date:
data de encerramento da LMP, baseada em AIJ_DTENCE ou próximo evento.

- engineering_status:
status calculado da Engenharia: ABERTA, FINALIZADA, PARCIAL ou RETORNADA.

- qtd_engineering_entries:
quantidade de passagens por eventos de Engenharia.

- qtd_engineering_closed:
quantidade de eventos de Engenharia encerrados ou com próximo evento global.

- qtd_advanced_from_engineering:
quantidade de vezes que avançou da Engenharia.

- qtd_returned_from_engineering:
quantidade de vezes que retornou da Engenharia.

- engineering_total_minutes:
soma do tempo em minutos nos eventos de Engenharia.

- qtd_pi:
quantidade de componentes PI calculada pela estrutura.

- nivel:
Nível 1, Nível 2 ou Nível 3 conforme QTD_PI.

- dias_uteis_sla:
SLA em dias úteis conforme nível.

- sla_minutos:
SLA em minutos sem tolerância.

- data_limite:
data limite base, sem tolerância.

- lead_time_util:
dias úteis entre start_date e end_date.

- status:
status de dashboard: Pontual, Atrasado, Andamento ou Retornada.

----------------------------------------------------------------------
14.25. TABELAS ADICIONAIS USADAS PELA API LMP
----------------------------------------------------------------------

Além das tabelas principais, a API LMP usa:

SA1010:
- cadastro de clientes;
- usada para enriquecer cabeçalho da LMP com nome do cliente.

Relação:
AD1.AD1_CODCLI = SA1.A1_COD
AD1.AD1_LOJCLI = SA1.A1_LOJA

SA3010:
- cadastro de vendedores;
- usada para enriquecer cabeçalho da LMP com nome do vendedor.

Relação:
AD1.AD1_VEND = SA3.A3_COD

SG1010:
- estrutura/BOM;
- usada para explodir estrutura e contar PIs.

Relação:
G1_COD = produto raiz PA
G1_COMP = componente

SB1010:
- usada em dois papéis:
1. produto da oportunidade;
2. produto raiz PA / componente PI da estrutura.

ADJ010:
- usada como origem dos produtos da LMP.

----------------------------------------------------------------------
14.26. REGRAS DE PRODUTO NA LMP
----------------------------------------------------------------------

Produtos da LMP são obtidos em ADJ010.

Campos de retorno esperados no GET LMP:
- group_code = SB1.B1_GRUPO
- code = SB1.B1_COD
- description = SB1.B1_DESC
- type = SB1.B1_TIPO
- qtd_pi = quantidade de PI vinculada ao produto

Regra:
- A lista de produtos deve ser ordenada por SB1.B1_COD.
- Cada produto pode ter sua própria QTD_PI.
- O total da LMP é a soma das QTD_PI por OV.

----------------------------------------------------------------------
14.27. REGRAS DE ORDENAMENTO
----------------------------------------------------------------------

Listagem LMP:
- ordenar por LMP_START_DATE DESC
- depois AD1_NROPOR DESC

Histórico:
- ordenar por revisão, data, hora, estágio e R_E_C_N_O_ conforme o objetivo:
- para exibição: mais recente primeiro;
- para cálculo interno: ordem global crescente.

Eventos âncora:
- escolher o mais recente por:
1. AIJ_REVISA DESC
2. AIJ_DTINIC DESC
3. AIJ_HRINIC DESC
4. R_E_C_N_O_ DESC

14.28. REGRAS PARA SQL MANUAL DO ESPECIALISTA
----------------------------------------------------------------------

- descrição do estágio;

- status;

3. Para diagnóstico, não filtrar apenas o estágio atual.

4. Para “aparece na LMP”, validar existência em LMPEventos.

5. Para “está em Engenharia agora”, usar AD1010 + AC2010.

6. Para “passou pela Engenharia”, usar AIJ010 + AC2010.

7. Para “dashboard”, calcular:
- QTD_PI;
- nível;
- SLA;
- status.

----------------------------------------------------------------------

Há dois conjuntos de status:

Status de Engenharia:

- RETORNADA

Status do Dashboard:

======================================================================
15. REGRAS DE DATA
======================================================================

Sempre usar datas no padrão YYYYMMDD nas SQLs.
Não usar formato YYYY-MM-DD dentro das consultas do Protheus, salvo se houver motivo técnico validado.

Campos de data principais:

- AD1010:
- AD1_DATA = data de inclusão
- AD1_DTINI = data de início
- AD1_DTFIM = data de encerramento

- AIJ010:
- AIJ_DTINIC = data de início do estágio
- AIJ_DTENCE = data de encerramento do estágio
- AIJ_DTLIMI = data limite do estágio

Para períodos mensais, usar intervalo fechado-aberto:

campo_data >= 'AAAAMM01'
campo_data < 'AAAAMM01 do mês seguinte'

Exemplo:
Março/2026:
campo_data >= '20260301'
campo_data < '20260401'

Nunca usar BETWEEN para mês fechado quando o padrão validado for intervalo fechado-aberto.

======================================================================
16. REGRAS DE FILTRO DE PERÍODO
======================================================================

### Hoje
campo_data = data atual no padrão YYYYMMDD

### Ontem
campo_data = data anterior no padrão YYYYMMDD

### Este mês
campo_data >= primeiro dia do mês atual
campo_data < primeiro dia do mês seguinte

### Mês passado
campo_data >= primeiro dia do mês anterior
campo_data < primeiro dia do mês atual

### Mês fechado
sempre usar intervalo fechado-aberto:
campo_data >= primeiro dia do mês
campo_data < primeiro dia do mês seguinte

### Intervalo informado pelo usuário
usar o campo correto da tabela escolhida:

- AD1010:
- AD1_DATA para data de inclusão
- AD1_DTINI para data de início
- AD1_DTFIM para data de encerramento

- AIJ010:
- AIJ_DTINIC para entrada no estágio
- AIJ_DTENCE para encerramento do estágio
- AIJ_DTLIMI para data limite do estágio

- ADJ010:
- normalmente não usar data como filtro principal

- AC1010:

### L) Modelo base para contagem de PI da LMP

WITH ProdutosLMP AS (
SELECT DISTINCT
ADJ.ADJ_FILIAL,
ADJ.ADJ_NROPOR,
ADJ.ADJ_REVISA,
ADJ.ADJ_PROD
FROM ADJ010 ADJ
WHERE
ADJ.D_E_L_E_T_ = ''
AND ADJ.ADJ_FILIAL = :FILIAL
AND ADJ.ADJ_NROPOR = :OV
),
ProdutosLMPRef AS (
SELECT
P.ADJ_FILIAL,
P.ADJ_NROPOR,
P.ADJ_REVISA,
P.ADJ_PROD,
SB1.B1_REFEREN
FROM ProdutosLMP P
INNER JOIN SB1010 SB1
ON SB1.D_E_L_E_T_ = ''
AND SB1.B1_COD = P.ADJ_PROD
WHERE
SB1.B1_REFEREN <> ''
),
ProdutosBase AS (
SELECT DISTINCT
R.ADJ_FILIAL,
R.ADJ_NROPOR,
R.ADJ_REVISA,
R.ADJ_PROD,
SB.B1_COD AS ROOT_PRODUCT
FROM ProdutosLMPRef R
INNER JOIN SB1010 SB
ON SB.D_E_L_E_T_ = ''
AND SB.B1_REFEREN = R.B1_REFEREN
AND SB.B1_TIPO = 'PA'
),
Recursive_BOM AS (
SELECT
B.ADJ_FILIAL,
B.ADJ_NROPOR,
B.ADJ_REVISA,
B.ADJ_PROD,
G.G1_COMP AS COMPONENT,
1 AS LEVEL
FROM ProdutosBase B
INNER JOIN SG1010 G
ON G.D_E_L_E_T_ = ''
AND G.G1_COD = B.ROOT_PRODUCT
AND G.G1_FIM > CONVERT(CHAR(8), GETDATE(), 112)

UNION ALL

SELECT
R.ADJ_FILIAL,
R.ADJ_NROPOR,
R.ADJ_REVISA,
R.ADJ_PROD,
G.G1_COMP,
R.LEVEL + 1
FROM SG1010 G
INNER JOIN Recursive_BOM R
ON R.COMPONENT = G.G1_COD
WHERE
G.D_E_L_E_T_ = ''
AND G.G1_FIM > CONVERT(CHAR(8), GETDATE(), 112)
AND R.LEVEL < 10
),
PI_COUNT_BY_PRODUCT AS (
SELECT
R.ADJ_FILIAL,
R.ADJ_NROPOR,
R.ADJ_REVISA,
R.ADJ_PROD,
COUNT(DISTINCT SB.B1_COD) AS QTD_PI
FROM Recursive_BOM R
INNER JOIN SB1010 SB
ON SB.D_E_L_E_T_ = ''
AND SB.B1_COD = R.COMPONENT
AND SB.B1_TIPO = 'PI'
GROUP BY
R.ADJ_FILIAL,
R.ADJ_NROPOR,
R.ADJ_REVISA,
R.ADJ_PROD
),
PI_COUNT_BY_OV AS (
SELECT
P.ADJ_FILIAL,
P.ADJ_NROPOR,
P.ADJ_REVISA,
SUM(P.QTD_PI) AS QTD_PI
FROM PI_COUNT_BY_PRODUCT P
GROUP BY
P.ADJ_FILIAL,
P.ADJ_NROPOR,
P.ADJ_REVISA
)
SELECT
ADJ_FILIAL,
ADJ_NROPOR,
ADJ_REVISA,
QTD_PI,
CASE
WHEN ISNULL(QTD_PI, 0) <= 10 THEN 'Nível 1'
WHEN ISNULL(QTD_PI, 0) <= 20 THEN 'Nível 2'
ELSE 'Nível 3'
END AS NIVEL,
CASE
WHEN ISNULL(QTD_PI, 0) <= 10 THEN 4
WHEN ISNULL(QTD_PI, 0) <= 20 THEN 8
ELSE 20
END AS DIAS_UTEIS_SLA,
CASE
WHEN ISNULL(QTD_PI, 0) <= 10 THEN 5760
WHEN ISNULL(QTD_PI, 0) <= 20 THEN 11520
ELSE 28800
END AS SLA_MINUTOS
FROM PI_COUNT_BY_OV;
